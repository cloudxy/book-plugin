# 0.5 实施记录

两条主线都使用现有模型：一条按用途蒸馏书籍/人物 Skill，一条编排调度这些 Skill 的生产步骤。正式作者分身及程序四闸仍走原合同。操作入口见 [production.md](../../../skills/book-workflow/references/production.md)。

0.5 试用包使用 `distilled-skill/2`（0.5.0 产出的 `/1` 包仍按原合同校验），不冒充 `book-skill/2` 正式作者分身；知识包不强制作者口吻。人物包需实际材料和真实产物，不能只登记姓名。逐字摘引在新线可选，所有声明正文仍进入阅读任务。

旧 `l1_extract.py`、`export_portfolio.py` 保留实验兼容，已标明不代表全文阅读或 Skill 可用性。`batch_runner.py` 读取新线的目标档位与生命周期，旧任务口径保留。

## 0.5.2 补齐的方案要求

0.5.0/0.5.1 已经交付执行链，但方案中“补阶段运行记录、失败归因、定向返修及工作流版本对照”的核心要求没有落实。真实运行中跨书反复出现的问题（复核包超出宿主输入上限、综合超时、休眠后租约过期、容量错误耗尽尝试次数、预算多次触顶）当时都靠私有脚本和手改策略解决，没有回到工作流。0.5.2 把这些问题收回工作流，修复内容见上表。

兼容性：

- 缓存键去掉了调度器和构建器源码的哈希，以及全局版本号。0.5.0 留下的键先用旧算法逐项核对，一致才换成新键。用三本私有运行状态的副本实测，已完成的 23、39、271 项全部核对通过，没有任何一项被判失效。0.5.0 时期的评测报告在新代码下重新核对，结论和证据哈希都没有变化。
- 已在跑的任务继续使用当初固定的扁平指令和旧结果合同，不会因为仓内模块文件更新而失效。其中复核包超过预算的那份副本（107 万字符）按新规则自动分成 6 批，每批不超过 19 万字符。
- `engine_hash()` 改为只对 0.4.0 解释器和构建依赖（`LEGACY_ENGINE`）取哈希，新线模块的改动不再改变正式候选的构建来源。影响：在此之前用全目录哈希构建的旧候选，下次运行 `build_candidate` 时签名会变，因此会重建；本工作区目前没有这样的旧候选。毛选 L3 任务仍按原候选与原合同继续，不因本次变更推定失效。

## 0.5.0 试产记录（历史）

0.5.0 当时记录的真实试产：两份书籍 Skill 和一份限定两封完整家书的人物 Skill，共 23 题、26 次逐轮回答。这些答文、评审和产线目录不在当前工作区，当前 `books/` 下也没有人物包，因此这份记录无法在当前工作区复核，只作为历史报告保留，不作为 0.5.2 的完成证据。之后在当前工作区跑的三本书中，一本通过了评测，两本在预算上限前未通过，详细记录都在私有目录。

0.5.0 还做过 3 题无 Skill 对照，属于小样本诊断：既不能据此宣称稳定优于通用模型，也没有建立降本或提速对照。

## 效果边界

- 命令执行器和当前宿主协助执行都有明确协议。没有执行器时不称无人值守；构建完成后仍须继续实际评测与交付。
- 能作为证据的是三样东西合在一起：声明的全文进入了输入、分段结果齐备、独立复核与抽查通过。不声称机器能证明模型理解了每个字。
- 默认预算有限。上下文过大或预算耗尽时保存断点并报告，不因预算自动缩小用户范围；`status` 的预估只是字符估计，不等于 token 或费用。
- 优化工具只是小规模反馈搜索加经验账本，没有完整实现 MIPRO/GEPA，也没有训练模型。只在一本书上验证过的规则不能推广为全局规则，候选不会被自动采纳，也不会静默修改已发布的包。
- 运行隔离按宿主的实际能力记录。新会话只拿到迁移包和当前任务，不等于已证明操作系统禁止访问原工作区。
- 时延、累计任务时间、实际 token、费用和人工干预分开衡量。并发不自动代表更省钱，不承诺固定提速倍数。

上游方法采用：nuwa `1.0.0`，核对提交 `7c7edfeb9d90a28b1f79e7847e1ba27a698cdc24`；采用材料分层、人物框架、适用边界和跨情境验证方向，按本仓私有交付与用途合同适配。cangjie 及其他 vendor 版本保持不变，没有修改其源码。
